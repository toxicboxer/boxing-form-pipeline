# Boxing Form Video Intelligence Pipeline — ハンズオン・イントロダクション

作成日: 2026-09-28 / 更新日: 2026-09-29
想定期間: 入社(11月)までの約6週間、基礎学習と並行して少しずつ進める

## 1. このプロジェクトの目的

自分と師範(倉本師範)のボクシング練習動画を比較し、フォームの差分を数値化・言語化するパイプラインを作る。
狙いは「画像 → 動画」「単一モデル → 複数モデルの組み合わせ」へ経験を広げることと、GitHub → Colab / AWS・GCP のGPU環境という開発・デプロイの流れを一通り経験すること。
題材の構造(お手本 vs 学習者の動作比較)は、入社先の作業動画解析ユースケース(熟練者と新人の比較分析)と同型なので、そのまま実務の予習になる。

## 2. 最終的に作るもの

```
動画 → フレームサンプリング → 人物検出 + トラッキング → 姿勢推定(キーポイント)
     → 時系列アライメント(DTW) → 関節角度の差分(構造化データ)
     → VLM(Qwen3-VL)による自然言語コメント生成
```

## 3. 進め方の原則

### 3-1. 開発の進め方(このプロジェクト専用のルール)

- **各Phaseでは、まず仕様のみを提示する。** 内容は「何を実装するか」「入力・出力」「利用するライブラリ/API」「調べるべき概念」「完了条件」の5点。
- **完成コードは先に出さない。** 実装前に具体的なコード例を提示して答えを誘導することもしない。
- **実装は自分で調査して行う。** 書いたコードを提示した後に、コードレビュー・バグ指摘・改善案・模範実装との比較を受ける。
- **詰まったときは、まずヒントと関連する公式ドキュメント/API名のみを受け取る。** 完成コードは、明示的に要求した場合のみ提示される。

### 3-2. 環境・運用の原則

- **Colab = アルゴリズムの試行錯誤、AWS/GCPのGPU = 実際に動くかの確認。** 各Phaseが動いた時点でクラウド側でも回す。
- **コードの実体は `src/` のPythonモジュール。** Colabノートブックは `git clone` して実行するだけの薄いランナーにする(ノートブック内にロジックを溜めない)。
- **GPUインスタンスは使う時だけ起動する。** 予算アラート(AWS Budgets / GCP予算アラート)を最初に設定しておく。
- **1Phase = 動く最小版を作る → pushする → クラウドで動かす。** 完成度より先に一周させる。

## 4. Phase一覧

| Phase | 内容 | 完了条件(要約) |
|---|---|---|
| 1 | 動画処理(フレームサンプリング) | 自分と師範の動画からフレームを抽出できる |
| 2 | 人物検出 + トラッキング | 動画内の人物にIDが付き、フレームをまたいで追跡できる |
| 3 | 姿勢推定 | 追跡した人物ごとにキーポイント時系列を保存できる |
| 4 | 時系列比較(DTW + 関節角度) | 自分と師範の差分を関節ごとの数値で出力できる |
| 5 | VLM統合 | 差分データ + 該当フレームからコーチングコメントを生成できる |
| 6 | 仕上げ(構造化出力・評価・コンテナ化) | 一連の処理がコンテナ1つで再現できる |
| 並行 | クラウド連携(GitHub → AWS/GCP) | pushをきっかけにGPUインスタンス上で実行確認できる |

## 6. Step 0: 環境の準備(所要 30〜60分目安)

1. GitHubに `boxing-form-pipeline` リポジトリを作成する(READMEを含めて初期化)。
2. 上記のディレクトリ構成を作り、`.gitignore` に `data/` を追加する(動画・個人情報をpushしない)。
3. `requirements.txt` の雛形を作る(必要なライブラリは各Phaseで自分で判断して追記していく)。
4. 練習動画を2本用意する(自分・師範)。**できるだけ同じ画角・同じ距離で撮影する**(カメラ位置の違いは、後のPhaseで単純な座標比較を難しくするため)。師範の映像は自分の練習用途に留め、公開する場合は事前に一言断る。
5. 予算アラートを設定する(クラウドを触り始める前に)。

## 7. Phase仕様

### Phase 1: 動画処理(フレームサンプリング)

**何を実装するか**
動画ファイルから、指定したFPS相当の間隔でフレームを間引いて抽出し、画像として保存するモジュール。各フレームが元動画のどの時刻に対応するかを、後のPhaseで参照できる形で残す。

**入力・出力**
- 入力: 動画ファイル(自分・師範の2本)、抽出したいFPS
- 出力: フレーム画像の保存先フォルダ(各画像のフレーム番号と時刻が分かること)、保存枚数

**利用するライブラリ/API**
- OpenCV: `cv2.VideoCapture`、`cv2.CAP_PROP_FPS`、`cv2.imwrite`
- ffmpeg: fps フィルタ(比較用)

**調べるべき概念**
- 動画のFPSとフレーム番号・時刻の関係
- VFR(可変フレームレート)の動画で、FPSの取得値が実際と食い違う場合があること
- スマートフォン撮影動画の回転メタデータの扱い
- 間引く間隔の決め方と、パンチのような速い動作をどれだけ取りこぼすか

**完了条件**
- [ ] 2本の動画からフレーム画像が保存されている
- [ ] 抽出枚数と動画の長さが整合していることを自分で確認した
- [ ] FPSを変えたときの表現力の違いを目視で比較した
- [ ] OpenCVとffmpegの結果を比較した
- [ ] ColabからGitHubのコードをcloneして実行できた
- [ ] 変更をpushする流れを一度通した

### Phase 2: 人物検出 + トラッキング

**何を実装するか**
フレーム列(または動画)から人物を検出し、フレームをまたいで同じ人物に同じIDを付けるモジュール。画面内に複数人いる場合でも、自分・師範を区別できる状態にする。

**入力・出力**
- 入力: Phase 1のフレーム画像列、または元の動画
- 出力: フレームごとの「人物ID・バウンディングボックス・信頼度」の記録

**利用するライブラリ/API**
- Ultralytics YOLO11(公式ドキュメントのDetect・Trackモード)
- トラッカー: ByteTrack(BoT-SORTとの比較も可)

**調べるべき概念**
- 物体検出(信頼度・NMS)とトラッキング(ID割り当て・データアソシエーション)の違い
- ByteTrackが低信頼度の検出も関連付けに使う考え方
- ID切り替わり(ID switch)が起きる条件
- 検出結果の保存形式(後のPhaseで読み込みやすい構造)

**完了条件**
- [ ] 動画内の人物にIDが付き、フレームをまたいで追跡できている
- [ ] ID切り替わりが起きたケースを1つ以上見つけ、原因を推測した
- [ ] 結果を描画した確認用動画を出力した
- [ ] 検出結果を後続Phaseが読める形式で保存した

### Phase 3: 姿勢推定

**何を実装するか**
追跡した人物ごとに関節キーポイントを抽出し、時系列として保存するモジュール。

**入力・出力**
- 入力: 動画(または フレーム画像列)、Phase 2の人物ID・バウンディングボックス
- 出力: 人物ID × フレーム × 関節の座標(と信頼度)の時系列データ

**利用するライブラリ/API**
- Ultralytics YOLO11-pose(公式ドキュメントのPoseモード)、または MediaPipe Pose のいずれか(両方試して比較してもよい)

**調べるべき概念**
- キーポイントの定義(COCO形式の17点など)と、モデルによる関節定義の違い
- 座標の正規化(画像サイズ・人物の大きさへの依存)
- 検出漏れ・信頼度が低いフレームの扱い(欠損補間など)
- 検出と姿勢推定を分ける構成 / 姿勢推定モデルに一括で任せる構成の違い

**完了条件**
- [ ] 人物IDごとにキーポイント時系列を保存できた
- [ ] 骨格を重ねて描画した確認用動画を出力した
- [ ] 欠損・低信頼度のフレームがどれくらいあるかを集計した

### Phase 4: 時系列比較(DTW + 関節角度)

**何を実装するか**
自分と師範のキーポイント時系列を、時間軸のずれを吸収して対応付け、関節ごとの差を数値化するモジュール。

**入力・出力**
- 入力: Phase 3の2人分のキーポイント時系列
- 出力: 関節(または関節角度)ごとの差分スコア、対応付けされたフレーム区間の情報(構造化データ)

**利用するライブラリ/API**
- DTW実装: 候補を自分で調べて選ぶ(Python向けのライブラリが複数ある)
- NumPy(角度計算)

**調べるべき概念**
- DTW(動的時間伸縮法)の仕組みと、窓幅などの制約
- 座標そのものではなく関節角度を特徴量にする理由(カメラ位置・体格・立ち位置への依存を減らす)
- パンチ1回分の区間への切り出し(セグメンテーション)を先に行うか否かの設計判断
- 差分スコアの正規化と、閾値の決め方

**完了条件**
- [ ] 2人分の時系列をDTWで対応付けできた
- [ ] 関節ごとの差分を数値で出力した
- [ ] 差が大きい区間を自分の目で動画と見比べて、数値と実感が一致するか確認した
- [ ] カメラ位置が違う場合に何が起きるかを、少なくとも1つ検証した

### Phase 5: VLM統合

**何を実装するか**
Phase 4の構造化された差分データと該当フレームをVLMに渡し、コーチング風の自然言語コメントを生成するモジュール。

**入力・出力**
- 入力: Phase 4の差分データ、差が大きい区間のフレーム画像(自分・師範)
- 出力: 差分の内容を踏まえたコメント(構造化された形式で保存)

**利用するライブラリ/API**
- Qwen3-VL(Hugging Face Transformersの公式ドキュメントを参照)
- 使用するモデルサイズは、Colabで使えるGPUメモリを確認したうえで自分で選ぶ

**調べるべき概念**
- VLMへの画像・動画入力の与え方(フレーム数・解像度と消費メモリの関係)
- 数値データを前提知識としてプロンプトに含める設計
- 生成コメントの評価方法(人手の確認、公開データの専門家コメントとの比較など)
- ハルシネーション(数値と食い違う記述)の検出方法

**完了条件**
- [ ] 差分データからコメントを生成できた
- [ ] 生成コメントが数値・映像と矛盾していないかを、自分で確認した
- [ ] 入力の与え方(フレーム数・数値の有無)を変えたときの違いを比較した

### Phase 6: 仕上げ(構造化出力・評価・コンテナ化)

**何を実装するか**
Phase 1〜5を1つのパイプラインとして通し、結果を構造化形式で出力する。Dockerコンテナ1つで再現できる状態にする。

**入力・出力**
- 入力: 自分と師範の動画2本
- 出力: 構造化された比較結果(差分・コメントなど)

**利用するライブラリ/API**
- Docker(NVIDIA GPUをコンテナから使う設定を含む)

**調べるべき概念**
- 各Phaseの入出力形式を揃えるための設計
- コンテナからGPUを使うための前提(ドライバ・ランタイム)
- 余裕があれば: 量子化などの推論最適化、軽量VLM(SmolVLMなど)でのエッジ想定の検証

**完了条件**
- [ ] 動画2本から最終出力までを1コマンドで実行できる
- [ ] コンテナ上でも同じ結果が再現できる
- [ ] 各Phaseの処理時間を計測した

### 並行トラック: クラウド連携(GitHub → AWS/GCP)

**何を実装するか**
GitHubへのpushをきっかけに、Dockerイメージをビルドしてコンテナレジストリに登録し、GPUインスタンス上で実行確認できる仕組み。

**入力・出力**
- 入力: GitHubリポジトリへのpush(または手動トリガー)
- 出力: レジストリ上のイメージ、GPUインスタンス上での実行結果

**利用するサービス/API**
- GitHub Actions(OIDCによるクラウド認証)
- AWS: ECR、GPU付きEC2 / GCP: Artifact Registry、GPU付きGCE
- 予算アラート: AWS Budgets / GCPの予算アラート

**調べるべき概念**
- OIDCで長期アクセスキーをSecretsに置かずに認証する仕組み
- コンテナレジストリとイメージのタグ付け
- GPUインスタンスの起動・停止と課金の関係、`workflow_dispatch` による手動起動
- IAMロール(GitHub Actions用 / インスタンス用)の最小権限

**完了条件**
- [ ] pushをきっかけにイメージがレジストリに登録される
- [ ] GPUインスタンス上でコンテナが起動し、Phase 1〜のいずれかの処理が動いた
- [ ] 使い終わったインスタンスを停止する手順を確立した
- [ ] 予算アラートが設定されている

着手のタイミング: Phase 1が動いてから、Phase 2の前後で始める。

## 8. 公開データセット(自分の動画の補助として)

主役は自分と師範の動画。公開データは、動画が揃う前の検証や、比較・評価の補助に使う。
ボクシングの師範と学習者を比較する構成に完全に一致する公開データは、調べた範囲では見つからなかった。

| データセット | 中身 | 使いどころ | 入手・ライセンス |
|---|---|---|---|
| UCF101 | ボクシング関連(Boxing Punching Bag / Boxing Speed Bag / Punch)を含む101カテゴリ、YouTube由来の13,320本。カメラの動きや視点の変化が大きい | Phase 1〜3の練習 | Hugging Face版はフレーム画像(320x240)。動画のまま使う場合は公式サイトから取得。データ自体のライセンスは未確認のため、公式ページで確認する |
| Fit3D | スタジオで4台の同期RGBカメラで撮影したフィットネス種目。認定インストラクター1名が基準、他は習熟度の異なる練習者 | Phase 4(指導者 vs 練習者の比較) | 非営利の研究ライセンス。IMARのFit3Dサイトで登録して入手 |
| FLAG3D | 60種類のフィットネス動作180K系列。スマートフォンの実環境動画と、動作ごとの文章での指導文あり | Phase 5(コメントの参考・比較) | 公開されている。ライセンス条件は未確認のため、公式ページで確認する |
| Ego-Exo4D | コーチ・教師による専門家コメントと熟練度ラベル付き。対象は料理・バスケ・サッカー・ダンス・音楽・ボルダリング(ボクシングはなし) | Phase 5(VLMコメントの評価用) | ライセンス契約への署名が必要(承認まで約2日)。データが大きいので一部のみ使う |
| Assembly101 | 組み立て・分解作業の動画4,321本(513時間)。ミス・修正・熟練度の違いを含む | 作業動画解析への応用(余裕があれば) | CC BY-NC 4.0 |

注意:
- Fit3D・Assembly101などは非営利ライセンス。個人の学習には使えるが、入社後に業務で使う場合は、その時点で条件を確認する。
- 「未確認」と書いたライセンスは、今回の調査では明記された条件を確認できていない。利用前に必ず公式ページで確認する。
